# 모바일 로컬 저장 전환

## 저장 모듈

`src/lib/local/`은 IndexedDB를 사용하는 로컬 저장 모듈이다. 현재 클라우드 스키마의
필드명과 금액·수량 계산 규칙을 유지한다. 금액은 원 단위이며 날짜는 `Date`, 사진은
별도 object store의 `Blob`으로 저장한다. 메타데이터에는 사진의 로컬 ID만 남긴다.

- `models.ts`: 데이터 타입, 필드·참조 무결성·중복 이름·판매 수량 검증
- `database.ts`: IndexedDB 초기화, 저장 완료 후 상태 공개, 사진과 데이터의 원자적 저장
- `repository.ts`: 기존 조회에서 필요한 필터·정렬·관계 조회와 CRUD
- `backup.ts`: 사진을 포함한 버전 3 백업, 버전 2 및 이전 품목/판매 백업 호환

조회는 메모리 스냅샷을 사용한다. 변경 작업은 최신 저장본의 복사본에서 실행하며,
실패하면 복사본을 버린다. IndexedDB 트랜잭션이 완료되기 전에는 저장 성공으로 처리하지
않는다. Web Locks로 탭 간 변경을 직렬화하고, 지원되지 않는 경우에도 리비전 비교로
오래된 데이터 덮어쓰기를 거절한다. BroadcastChannel로 다른 탭에 갱신을 알린다.

새 백업은 `schemaVersion: 3`, `exportedAt`, `data`, `images`를 갖는다. `data`에는
기존 11개 테이블과 예산·구매 후보 3개 테이블의 원본 레코드가 모두 들어가고 `images`에는 사진의 data URL이 들어간다.
불러오기 전에 날짜·수량·금액·중복 ID·부모 참조·사진 누락을 검사한다.

## 기존 클라우드 데이터 이전

기존 앱의 백업은 **품목과 판매만** 내보낸다. 행사, 체크리스트, 미사용 카탈로그,
카탈로그 순서, 발송 그룹 이름까지 보존하려면 아래 전체 내보내기를 사용한다.
클라우드 DB와 사진은 읽기만 하며 삭제하거나 수정하지 않는다.

1. **로컬 버전을 배포하기 전에** 기존 환경변수가 있는 개발 컴퓨터에서 실행한다.

   ```bash
   npm --prefix tools/cloud-export install
   node --env-file=.env.local tools/cloud-export/export.mjs /tmp/expense-tracker-full.json
   ```

   Node.js 20.9 이상을 사용한다. `.env.local`의 `DIRECT_URL` 또는 `DATABASE_URL`이
   필요하다. 사진 하나라도 내려받지 못하면 불완전한 백업 파일을 만들지 않는다.

2. JSON을 모바일 기기에 안전하게 옮긴다. 파일에는 구매 기록과 사진이 들어 있다.
3. 로컬 버전의 앱을 사용할 모바일 브라우저/PWA에서 백업 화면을 열어 JSON을 불러온다.
4. 품목·판매·행사·카탈로그·사진을 확인하고 새 로컬 백업도 저장한다.
5. 이전 결과를 확인한 뒤 사용자가 직접 클라우드 서비스와 기존 환경변수를 정리한다.

기존 앱에서 내려받은 `{ exportedAt, items }` 형식도 읽을 수 있다. 이 경우 품목에
사용된 카탈로그를 다시 만들고 발송 그룹 이름은 임시 이름으로 복구한다. 백업에 없는
행사·체크리스트·원래 카탈로그 순서는 복구할 수 없다. 사진 URL이 들어 있으면 가져오기
중에만 인터넷으로 내려받아 로컬 사진으로 변환한다. 다운로드 실패 시 기존 로컬
데이터는 그대로 유지한다.

## 데이터 보관 범위

로컬 데이터는 **기기·브라우저·사이트 주소별**로 분리된다. 모바일과 컴퓨터 간 자동
동기화는 없으며 옮길 때는 JSON 백업을 사용한다. 브라우저 데이터 삭제, 시크릿 모드 종료,
기기 분실, 도메인 변경에 대비해 앱 밖에 백업을 보관한다. 앱 캐시와 IndexedDB는 별개이며
앱 파일을 업데이트할 때 사용자 데이터 저장소를 지우지 않는다.

## 검증

```bash
npx tsc --noEmit -p .
npm test
```

테스트는 실제 사용자 IndexedDB와 클라우드에 연결하지 않는다. 모의 IndexedDB에서
저장 완료 시점, 롤백, 사진 정리, 관계 조회, 연쇄 삭제, 백업 호환과 손상 입력을 검사한다.

## 배포 빌드

Vercel의 Build Command는 `npm run build`를 사용한다. Next.js 빌드 후
`scripts/build-service-worker.mjs`가 오프라인용 `public/sw.js`를 생성한다.
이 파일은 Git에 저장하지 않으며, 새 체크아웃에는 `public` 폴더도 없을 수 있으므로
스크립트가 폴더를 먼저 생성한다. 완료 시 `Generated public/sw.js` 로그가 출력된다.

Next.js 페이지 목록까지 출력된 뒤 빌드가 실패하면 그 아래의 서비스 워커 생성 로그도
확인한다. `ENOENT ... public/sw.js` 오류는 출력 폴더가 없을 때 발생했던 문제로,
폴더 자동 생성 수정이 포함된 최신 커밋으로 배포하면 해결된다.
`npm test`에는 출력 폴더가 없는 최초 빌드와 폴더가 있는 재빌드 검증이 포함되어 있다.

## 화면 스크롤

품목 등록(`/items/new`) 화면은 들어갈 때마다 맨 위에서 시작한다.
다른 화면은 기존처럼 URL별로 기억한 스크롤 위치를 복원한다.

## 이전 백업에서 누락된 행사만 복구

Supabase의 `Event`, `EventChecklistItem`에 원본이 남아 있다면 아래 순서로 복구한다.

1. 휴대폰 앱의 **백업 → 전체 백업 다운로드**로 현재 기록을 먼저 보관한다.
2. 컴퓨터에서 프로젝트 폴더의 터미널을 열고 실행한다.

   ```bash
   npm --prefix tools/cloud-export ci
   node --env-file=.env.local tools/cloud-export/export-events.mjs /tmp/expense-tracker-events.json
   ```

   `.env.local`에 기존 `DIRECT_URL` 또는 `DATABASE_URL`이 필요하다.
   이 명령은 클라우드의 행사와 체크리스트만 읽는다. 사진 다운로드와 DB 수정은 하지 않는다.
   완료 메시지의 행사·체크리스트 개수를 확인한다. 같은 이름의 출력 파일이 있으면 중단하므로,
   다시 내보낼 때는 다른 파일명을 지정한다.
3. `/tmp/expense-tracker-events.json`을 휴대폰으로 옮긴다.
4. 이 기능이 포함된 버전을 배포하고 휴대폰 앱의 업데이트를 적용한다.
5. **백업 → 누락된 행사만 복구**에서 파일을 선택하고 추가할 개수를 확인한다.
   **불러오기 (기존 데이터 교체)**가 아니라 **행사만 추가** 버튼을 누른다.
6. 행사 목록과 체크리스트를 확인하고 다시 전체 백업을 다운로드한다.

기존 품목·판매·사진·카탈로그·발송 그룹은 유지한다. 같은 ID의 행사가 이미 있으면
그 행사와 체크리스트 전체를 건너뛰므로, 재실행해도 중복되거나 기기의 체크 상태가
과거 값으로 돌아가지 않는다. 이름이 같더라도 ID가 다르면 별도 행사로 추가된다.
연결된 품목이 기기에 없거나 체크리스트 ID가 충돌하면 전체 추가를 중단한다.
품목을 임의로 새로 만들거나 연결을 삭제하지 않으며, 실제 저장 직전 최신 기기 데이터로
다시 검사한다. 행사와 체크리스트는 하나의 트랜잭션으로 저장한다.

## 평소에는 전체 백업 한 번으로 보관

행사 복구를 마친 뒤부터는 휴대폰의 **백업 → 전체 백업 다운로드**만 사용하면 된다.
현재 기기에 저장된 행사·체크리스트(완료 체크, 부스, 금액, 수량, 품목 연결 포함)와
품목·판매·사진 등이 하나의 JSON 파일에 함께 들어간다. 행사 전용 내보내기는
예전 백업에서 빠진 기록을 처음 복구할 때만 필요하다.

다운로드 버튼 위에서 현재 기기의 행사·체크리스트 개수를 확인할 수 있다.
파일 생성 후 표시되는 개수는 실제 내보낸 데이터 기준이며, 같은 파일을
**백업 불러오기**에서 선택만 해도 행사·체크리스트 개수를 다시 확인할 수 있다.
확인만 할 때는 **불러오기 (기존 데이터 교체)**를 누르지 않는다.
기기에 행사 2개·체크리스트 35개가 있다면 두 화면에서도 그 개수가 보여야 한다.
다른 기기나 다른 브라우저에서 백업하면 그곳의 데이터가 저장되므로 복구한 휴대폰에서 진행한다.

내보내기 전에 모든 테이블과 연결을 검사한다. 버전 2·3 백업에서 행사 또는 체크리스트
목록 자체가 빠진 파일은 복원을 거절한다(정상적으로 빈 목록인 경우와 구분).
자동 모바일 테스트는 행사 2개·체크리스트 35개를 포함한 전체 백업을 다운로드하고
빈 브라우저에 복원한 뒤 다시 내보내 원본 데이터와 사진이 모두 같은지 비교한다.
이전 버전의 품목·판매 전용 파일은 행사 누락과 현재 행사 삭제에 대한 안내를 표시한다.

## 월별 예산과 구매 후보

대시보드의 **예산·구매 후보 관리**에서 사용한다. 새 라이브러리나 클라우드 연결은 없다.

1. **확인할 월**을 선택하고 **예산 설정**을 연다.
2. **기본 월 예산**을 만원 단위로 입력한다(예: `30` = 300,000원).
   선택한 월부터 적용되며, 과거 달의 설정은 바꾸지 않는다. 기본 예산 변경은 이번 달부터
   가능하다. 미래 달을 선택해 미리 변경을 예약할 수도 있다.
3. 행사 등으로 특정 달만 금액을 달리하려면 **이 달 예산 저장**을 사용한다.
   달별 설정이 기본 예산보다 우선한다. **이 달 별도 예산 해제**로 기본값을 다시 따른다.
   예산 0원과 예산 미설정은 구분하며, 남은 예산은 자동 이월하지 않는다.
4. 대시보드에서 사용 금액·남은 금액·사용률을 확인한다. 80% 이상이면 주의 문구,
   초과하면 초과 금액을 표시한다. 판매 수입으로 구매 예산을 자동 증가시키지 않는다.
5. 구매 전 **후보 추가**로 이름·예정 월·예상 단가·수량·배송비·이유·우선순위·마감일·링크를
   기록한다. 후보를 체크하면 모두 구매했을 때의 잔액을 계산한다. 아직 실제 지출에는 포함하지 않는다.
6. **구매하고 품목 등록**을 누르면 이름·금액·수량·배송비·링크·이유가 미리 채워진다.
   장르·캐릭터·물품 종류와 실제 구매일을 확인하고 저장한다. 품목 등록에 성공한 경우에만
   후보가 구매 완료가 되며, 같은 후보로 두 번 등록하지 못한다. 중간에 취소하거나 저장에
   실패하면 후보는 유지된다. 이미 완료한 후보는 **구매 완료한 후보**에서 품목으로 이동한다.

예산 계산은 월별 추이와 동일하게 구매일의 월(저장된 날짜의 ISO 연·월) 기준으로
`단가 × 구매 수량 + 배송비`를 합산한다. 판매 기록·구매 후보·행사 체크리스트는
별도로 더하거나 빼지 않는다. 체크리스트만 작성한 실제 구매는 품목 등록이 필요하다.
구매일 없는 품목은 제외 개수를 표시한다. 미확정 배송비는 추가 가능성을 표시하며,
배송비를 나중에 입력하면 해당 품목의 구매월 지출이 바뀐다.
품목 수정 시 기존 금액을 제외하고 새 금액으로 계산한다. 예산을 초과해도 실제 구매 기록은
저장할 수 있다. 이 기능의 예산은 앱에 등록한 구매 범위이며, 은행 거래를 자동으로 가져오지 않는다.

`budgetRule`(적용 시작 월별 기본 예산), `monthlyBudget`(달별 별도 예산), `wish`(구매 후보)를
기존 IndexedDB 스냅샷에 함께 저장한다. 이전 기기 데이터는 새 테이블만 빈 목록으로
보완하고, 기존 품목·행사·사진을 보존한다. 전체 백업 버전은 3이며 예산과 구매 후보도 포함한다.
버전 2와 품목/판매 전용 백업은 예산·구매 후보가 없는 상태로 읽을 수 있다. **전체 교체**이므로
오래된 백업을 불러오면 현재 예산·구매 후보도 교체된다. 버전 3 파일에서 새 테이블이
누락되면 복원을 거절한다. 버전 3 백업을 복원할 기기의 앱도 최신 버전이어야 한다.

검증은 과거 예산 보존, 별도 0원 예산, 구매일 이동, 판매·행사 중복 합산 방지, 기존 저장본
보완, 백업 버전 호환, 후보 중복 구매 방지, 품목 편집 시 중복 계산 방지, 오프라인 사용,
예산·구매 후보를 포함한 새 기기 복원을 포함한다.
